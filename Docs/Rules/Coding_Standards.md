# C# Coding Standards

이 문서는 C# 코드를 새로 작성하거나, 기존 코드에 주석을 추가하거나 수정할 때 적용합니다.

## 1. 기본 코딩 원칙

- C#의 일반적인 명명 규칙을 따릅니다.
- 클래스, 메서드, 변수는 역할을 명확하게 표현하는 이름을 사용합니다.
- 하나의 클래스와 메서드는 가능한 한 명확한 책임을 갖도록 설계합니다.
- 불필요한 중복 코드와 과도한 추상화를 피합니다.
- 기존 프로젝트의 코딩 스타일을 우선적으로 따릅니다.
- 새 파일을 작성하기 전에 같은 폴더의 기존 스크립트가 있으면 1개 이상 읽고 스타일을 확인합니다.
- 코드의 짧음보다 가독성과 유지보수성을 중요하게 생각합니다.
- 코드의 식별자(클래스, 메서드, 변수 이름)는 영어, 주석과 설명은 한국어로 작성합니다.
- 지시나 `Docs/Architecture/Decisions.md`에 없는 사항(타입, static 여부, 폴더 경로 등)은 임의로 정하지 않고 "미결정"으로 표시합니다.

## 2. 명명 규칙

| 대상 | 규칙 | 예시 |
|---|---|---|
| 클래스 / 구조체 | PascalCase | `PlayerController` |
| 인터페이스 | `I` + PascalCase | `IDamageable` |
| 열거형(enum) 이름 | PascalCase | `EntityState` |
| 열거형 값 | PascalCase | `Alive` |
| 메서드 | PascalCase | `CalculateMovement()` |
| 프로퍼티 | PascalCase | `MoveSpeed` |
| public 필드 | PascalCase | `MoveSpeed` |
| private 필드 | camelCase (`_` 접두사 없음) | `moveSpeed`, `movement` (`_movement`는 위반) |
| 지역 변수, 매개변수 | camelCase | `currentSpeed` |
| 상수 (`const`) | PascalCase | `MaxInventorySize` |

기존 프로젝트에서 일관된 명명 규칙을 사용하고 있다면 새로운 규칙보다 기존 규칙을 우선합니다.

단, 기존 코드가 이 표와 다를 때 사용자가 요청하지 않은 이름 변경은 하지 않고 다른 점만 알립니다.

## 3. 코드 책임과 가독성

- 메서드는 약 40줄 이내를 기본으로 합니다. 넘으면 책임이 섞였는지 확인합니다.
- 중첩 조건문은 3단계 이내를 기본으로 합니다. 조기 반환(early return)으로 줄입니다.
- 메서드 이름만으로 기능을 예상할 수 있도록 작성합니다.
- 매직 넘버 대신 의미 있는 상수나 설정값을 사용합니다.
- 다른 클래스의 내부 구현에 불필요하게 의존하지 않습니다.
- 코드의 실행 순서와 데이터 흐름을 파악하기 쉽게 작성합니다.

## 4. 주석 작성 원칙

주석의 목적은 코드를 그대로 번역하는 것이 아니라 코드의 역할과 설계 의도 및 사용된 API와 문법의 동작을 이해하도록 돕는 것입니다.

**클래스 주석**
- 클래스가 담당하는 역할과 존재 이유를 설명합니다.

**주요 변수 주석**
- 변수에 저장되는 데이터의 의미를 설명합니다.
- 이름만으로 의미가 명확한 변수에는 주석을 작성하지 않습니다.

**주요 메서드 주석**
- 메서드가 수행하는 작업과 필요한 경우 입력 및 반환값의 의미를 설명합니다.

**핵심 로직 주석**
- 복잡한 계산, 처리 순서 및 설계 이유를 설명합니다.
- 코드만 읽어서는 의도를 알기 어려운 부분을 중심으로 작성합니다.

**API 및 C# 문법 설명 주석**
- Unity API, C# 함수, 프로퍼티, 생성자, 연산자 및 생소한 문법을 사용하면 해당 요소 자체가 무엇인지 설명합니다.
- 함수는 어떤 기능을 수행하는지, 매개변수는 무엇을 의미하는지, 반환 자료형과 반환값은 무엇인지 설명합니다.
- 프로퍼티는 어떤 데이터를 가져오거나 설정하는지, 데이터의 자료형과 동작 방식을 설명합니다.
- 생성자는 어떤 객체를 생성하며 전달받은 매개변수가 어떻게 사용되는지 설명합니다.
- 연산자와 문법은 어떤 규칙으로 값을 처리하는지 설명합니다.
- API의 주요 동작 방식과 주의할 점이 있다면 함께 설명합니다.
- 유사한 API 사이에 동작 차이가 있다면 차이점과 현재 방식을 선택한 이유를 설명합니다.
- 초보자가 해당 API나 문법을 처음 접하더라도 주석을 읽고 기본적인 사용 방법과 동작을 이해할 수 있도록 작성합니다.
- 동일한 API를 반복해서 사용할 때는 이미 설명한 내용을 매번 반복하지 않아도 됩니다.
- 실제 Unity 버전과 C#의 동작을 기준으로 설명하며, 확인되지 않은 내용을 추측하지 않습니다.

**주석 작성 시 주의 사항**
- 한국어를 사용합니다.
- 초보자도 실행 흐름을 이해할 수 있도록 명확하게 작성합니다.
- 모든 코드 줄에 주석을 붙이지 않습니다.
- 코드와 동일한 내용을 반복하는 주석은 피합니다.
- 코드가 변경되면 관련 주석도 함께 확인합니다.
- API 설명은 실제 동작을 기준으로 작성하고, 확인되지 않은 동작을 추측하여 설명하지 않습니다.

**금지 항목**
- 주석에 수정 이력이나 작업 메모("수정:", "변경:", "추가:", "기존 ~ 금지")를 쓰지 않습니다.
- 주석은 현재 코드의 목적과 동작 이유만 설명하며, 과거 코드에 대한 이야기를 쓰지 않습니다.
- 기존 코드를 수정할 때 변경과 맞지 않게 된 낡은 주석은 함께 고치거나 삭제합니다.

**서식**
- `<summary>`를 쓸 때는 `///` 줄의 들여쓰기를 대상 선언과 같은 칸에 맞춥니다.
- 주석을 추가한 뒤 파일을 다시 읽어 들여쓰기와 서식이 깨지지 않았는지 확인합니다.

**좋은 예와 나쁜 예**

```csharp
// 나쁜 예: 코드를 그대로 번역
generations[index]++; // generations[index]를 1 증가시킨다

// 나쁜 예: 작업 메모
rb.linearVelocity = movement; // 수정: velocity 대신 linearVelocity 적용 (기존 velocity 사용 금지)

// 좋은 예: 의도를 설명
generations[index]++; // 해제된 슬롯의 옛 핸들이 새 엔티티로 오인되지 않도록 세대 번호를 올린다

// 좋은 예: 현재 코드의 이유를 설명
rb.linearVelocity = movement; // Unity 6에서는 Rigidbody2D의 선형 속도를 linearVelocity로 읽고 설정합니다.
```

**API 설명 주석 예시**

```csharp
// Input.GetAxis(string axisName):
// Unity Input Manager에 설정된 입력 축의 값을 가져오는 함수입니다.
// "Horizontal"은 좌우 입력, "Vertical"은 상하 입력을 의미합니다.
// 반환 자료형은 float이며, 기본 설정에서는 -1.0부터 1.0 사이의 값을 반환합니다.
// 입력값이 부드럽게 변화하도록 보정하므로 키를 놓아도 값이 즉시 0이 되지 않습니다.
float moveX = Input.GetAxis("Horizontal");
```

```csharp
// GetComponent<T>():
// 현재 GameObject에 연결된 컴포넌트 중 지정한 타입 T의 컴포넌트를 검색하는 함수입니다.
// 검색에 성공하면 해당 컴포넌트를 반환하고, 찾지 못하면 null을 반환합니다.
rb = GetComponent<Rigidbody2D>();
```

```csharp
// Vector2.normalized:
// 현재 벡터의 방향은 유지하면서 크기(Magnitude)를 1로 정규화한 Vector2를 반환하는 프로퍼티입니다.
// 벡터의 크기가 0이면 정규화된 결과도 0 벡터입니다.
Vector2 direction = movement.normalized;
```

## 5. 설명 및 대안 비교

실제 프로젝트 구현이 끝난 뒤의 설명 형식은 `Docs/Workflow/Approval_Process.md` 6번을 따릅니다.

사용자가 수정 대상과 내용을 구체적으로 지정한 확정 수정에서는 변경한 줄과 이유만 짧게 설명합니다.

- 새로운 C# 문법이나 생소한 API를 사용하면 사용 이유와 주요 동작 방식을 한 줄 이상으로 설명합니다.
- 복잡한 기능은 작은 단계로 나누어 설명합니다.
- 대안 비교는 신규 시스템 설계처럼 선택지가 실제로 갈릴 때만 합니다. 하나의 방법만 정답처럼 제시하지 않되, 실질적인 차이가 없으면 억지로 추가하지 않습니다.
- 사용자가 이해하기 어려운 불필요한 추상화는 피합니다.
- 코드 작성 자체가 학습을 대신하지 않도록, 사용자가 직접 이해하고 설명할 수 있는 수준으로 안내합니다.

## 6. 성능과 메모리 관리

- 불필요한 객체 생성을 피합니다.
- 반복 처리에서 GC Alloc 발생 가능성을 고려합니다.
- LINQ, 문자열 연결, 박싱 등 할당이 발생할 수 있는 코드를 주의합니다. (Update 계열 금지 패턴은 `Docs/Rules/Unity_Rules.md` 6.1을 따릅니다.)
- 성능 최적화가 필요한 부분은 실제 측정 후 개선합니다.
- 가독성과 성능 사이의 균형을 고려합니다.

성능 측정 및 테스트 절차는 `Docs/Workflow/Testing.md`를 따릅니다.
