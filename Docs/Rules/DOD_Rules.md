# DOD Development Rules

## 1. 기본 설계 방향

이 프로젝트는 DOD(Data-Oriented Design)를 중심으로 설계하며, Unity의 MonoBehaviour와 결합하는 Hybrid Architecture를 사용합니다.

대량의 게임 데이터는 객체 단위의 상속 구조보다 연속된 메모리와 데이터 중심으로 관리하는 것을 우선합니다.

확정된 설계 결정은 `Docs/Architecture/Decisions.md`를 따릅니다. 이 문서와 Decisions.md가 어긋나면 Decisions.md를 우선합니다.

## 2. 데이터 구조 규칙

- 대량으로 생성되거나 반복 처리되는 데이터는 `struct`를 우선 고려합니다.
- 데이터 저장에는 배열을 우선적으로 사용합니다.
- 불필요한 클래스 상속 구조를 만들지 않습니다.
- 데이터와 데이터 처리 로직을 분리합니다.
- 데이터 구조는 실제 사용 목적과 접근 패턴을 고려하여 설계합니다.
- 무조건 `struct`를 사용하는 것이 아니라 크기, 복사 비용, 수명 및 사용 방식을 고려합니다.
- `struct`에는 값 타입 필드만 넣습니다. `string`, `class` 참조, `List`는 넣지 않습니다.
- 배열 속 `struct`를 수정할 때는 복사본이 아니라 원본을 수정합니다. (`arr[i].field = value` 또는 `ref` 사용. `var e = arr[i]; e.field = value;`는 원본이 바뀌지 않으므로 금지)
- `uint`와 `int`를 섞어 쓰지 않습니다. 인덱스와 카운트는 `int`로 통일합니다.

## 3. 데이터 처리 규칙

- 데이터 처리 로직은 가능한 한 Unity 객체에 의존하지 않도록 설계합니다.
- 상태(배열, 카운터 등)를 가지는 시스템은 인스턴스 클래스로 만듭니다.
- `static` 메서드는 상태를 가지지 않는 순수 계산(입력 값만으로 결과를 내는 함수)에만 사용합니다.
- 반복 처리에서 불필요한 메모리 할당을 최소화합니다.
- 데이터 처리 과정에서 GC Alloc이 발생하는 지점을 고려합니다.
- 데이터 변경과 조회의 책임을 명확하게 구분합니다.
- 지시나 Decisions.md에 없는 사항(static 여부, 타입, 용량 등)은 임의로 정하지 않고 "미결정"으로 표시합니다.

## 4. MonoBehaviour와의 역할 분리

DOD와 MonoBehaviour는 서로 대체하는 구조가 아니라 역할을 분담합니다.

**DOD 영역**
- 게임 데이터 저장
- 대량 데이터 처리
- 반복적인 계산 및 데이터 갱신
- Unity 객체에 의존하지 않는 로직

**MonoBehaviour 영역**
- Unity 생명주기 관리
- GameObject 및 Component 연결
- Transform, Rigidbody2D 등 Unity API 연동
- 입력, 물리 및 화면과 데이터 시스템 연결

실제 시스템별 책임과 연결 관계는 `Docs/Architecture/Overview.md`에 기록합니다.

## 5. 성능 고려 사항

- 불필요한 힙 메모리 할당을 줄입니다.
- 반복문 내부에서 불필요한 객체 생성을 피합니다.
- 배열의 크기와 데이터 접근 패턴을 고려합니다.
- 데이터 복사 비용이 큰 구조는 주의합니다.
- 성능 최적화는 실제 측정 결과를 바탕으로 진행합니다.

## 6. 설계 시 주의 사항

- DOD를 적용하기 위해 구조를 지나치게 복잡하게 만들지 않습니다.
- 데이터 크기와 접근 빈도를 고려하지 않고 무조건 배열로 통일하지 않습니다.
- 실제 요구 사항 없이 시스템 구조나 데이터 필드를 미리 확정하지 않습니다.
- 기존 아키텍처를 변경할 때는 사용자 승인을 받습니다.
- 구체적인 구현 구조는 실제 코드와 일치하도록 Architecture 문서를 갱신합니다.
