# AI Development Workflow & Approval Process

## 1. 기본 작업 원칙

AI는 단순히 코드를 빠르게 생성하는 것이 아니라, 사용자가 프로젝트의 설계와 구현을 이해할 수 있도록 개발을 보조합니다.

- AI가 코드 구현을 담당할 수 있습니다.
- 사용자는 코드의 구조와 실행 원리를 이해할 수 있어야 합니다.
- 구현 속도보다 이해 가능한 설계와 검증 가능한 결과를 중요하게 생각합니다.
- AI가 제안하는 설계가 항상 정답이라고 가정하지 않습니다.
- 더 나은 대안이 있다면 장단점을 비교하여 설명합니다.

## 2. 작업 시작 전 확인

작업을 시작하기 전에 다음 사항을 확인합니다.

1. 사용자가 요청한 기능과 작업 범위를 파악합니다.
2. 기존 코드와 프로젝트 구조를 확인합니다.
3. `AGENTS.md`와 현재 작업에 필요한 상세 문서를 확인합니다.
4. 기존 시스템과 중복되거나 충돌하는 부분이 있는지 확인합니다.
5. 구현에 필요한 정보가 부족하면 임의로 결정하지 않고 사용자에게 질문합니다.

## 3. 신규 기능 및 시스템 생성

새로운 기능이나 시스템을 구현하기 전에는 다음 내용을 사용자에게 설명합니다.

1. 구현하려는 기능의 목적
2. 필요한 클래스와 파일 구성
3. 각 클래스의 역할과 책임
4. 데이터의 저장 및 전달 방식
5. 시스템 간 연결 관계
6. 설계를 선택한 이유
7. 다른 구현 방법과 비교한 장단점
8. 예상되는 성능 및 유지보수 측면의 주의 사항

설계 설명 후 사용자 승인을 요청합니다.

승인받기 전에는 실제 프로젝트 파일을 생성하거나 수정하지 않습니다.
사용자가 "승인", "진행해" 등으로 명시한 경우에만 승인으로 봅니다.

설계안은 요청받은 기능의 범위 안에서만 작성합니다.

### 3.1 설계 검토 및 범위 제한

설계안을 작성하거나 수정할 때 다음 절차를 따릅니다.

1. 관련 설계 문서와 `Docs/Architecture/Decisions.md`를 먼저 확인합니다.
2. 검토 범위는 사용자가 요청한 기능과, 그 기능이 직접 사용하는 인터페이스까지로 한정합니다.
3. 확정된 결정(`Decisions.md`)과 어긋나는 내용은 작성하지 않습니다. 어긋나는 부분이 필요해 보이면 설계에 반영하지 않고 먼저 보고합니다.
4. 요청 범위 밖 시스템의 구조 변경이 필요해 보이면 설계를 확장하지 않습니다. "선행 작업 필요"로 보고하고 멈춥니다.
5. 이미 확정된 결정은 사용자가 변경을 요청하기 전에는 다시 논의하지 않습니다.
6. 사용자가 지적한 항목은 지적된 범위만 수정하고, 수정하지 않은 부분은 그대로 유지합니다.
7. 설계안 끝에 확정된 결정과의 대조표(결정 번호, 근거 문장, 일치 여부)를 출력합니다.
8. 설계 검토 중에는 코드나 문서를 수정하지 않습니다.

발견한 문제 중 현재 요청 범위 밖의 것은 "별도 제안"으로 한 줄씩 목록만 남기고, 이번 설계에 포함하지 않습니다.

## 4. 기존 기능 수정

기존 기능의 동작을 변경하는 경우 다음 절차를 따릅니다.

1. 기존 코드의 실행 흐름을 확인합니다.
2. 현재 동작과 수정이 필요한 이유를 설명합니다.
3. 수정할 파일과 변경 범위를 제시합니다.
4. 다른 시스템에 미칠 영향을 설명합니다.
5. 사용자 승인을 받은 뒤 수정합니다.

단, 기존 동작에 영향을 주지 않는 단순 오타, 주석 및 포맷 수정은 별도 승인 없이 처리할 수 있습니다.

## 5. 아키텍처 변경

다음과 같은 변경은 아키텍처 변경으로 취급합니다.

- 클래스의 책임 변경
- 데이터 저장 방식 변경
- 시스템 간 의존 관계 변경
- 기존 시스템 통합 또는 분리
- 핵심 데이터 구조 변경

이러한 변경은 영향 범위를 먼저 분석하고 반드시 사용자 승인을 받습니다.

## 6. 코드 구현 및 설명

코드를 구현한 뒤에는 다음 내용을 설명합니다.

1. 생성하거나 수정한 파일
2. 각 클래스와 메서드의 역할
3. 코드가 실행되는 순서
4. 데이터가 전달되고 처리되는 과정
5. 주요 설계 선택의 이유
6. 사용한 C# 문법과 Unity API 중 학습할 내용
7. 다른 구현 방법과의 차이

설명 분량은 작업 규모에 비례합니다. 작은 변경은 1~2번과 5번만 간략히 설명하고, 새 시스템 구현 시에만 7개 항목을 모두 설명합니다.

코드에는 `Docs/Rules/Coding_Standards.md`에 정의된 주석 규칙을 적용합니다.

설명은 사용자가 코드를 직접 읽고 이해할 수 있도록 작성합니다.

## 7. 학습 및 이해 확인

- 새로운 개념은 필요한 경우 작은 예제로 설명합니다.
- 복잡한 실행 흐름은 단계별로 나누어 설명합니다.
- 사용자가 직접 코드를 분석하거나 수정해 볼 수 있는 실습을 제안할 수 있습니다.
- 면접에서 질문받을 수 있는 설계 이유와 기술적 선택을 함께 정리합니다.
- 사용자가 원하지 않는 경우 불필요한 퀴즈나 확인 질문을 강요하지 않습니다.

## 8. 작업 완료 및 추가 작업

- 승인받은 작업 범위만 구현합니다.
- 추가 개선 사항이 발견되면 현재 작업에 임의로 포함하지 않고 별도로 제안합니다.
- 구현이 끝나면 변경 사항과 테스트 결과를 보고합니다.
- 테스트하지 않은 부분은 미검증이라고 명시합니다.
- 후속 작업이 필요하면 다음 작업의 목적과 이유를 설명합니다.
