# Git Workflow Rules

## 1. 기본 원칙

Git은 프로젝트의 변경 이력을 관리하고 작업 내용을 안전하게 보존하기 위해 사용합니다.

- `main` 브랜치는 항상 안정적인 프로젝트 상태를 유지합니다.
- `main` 브랜치에서 직접 기능 개발 및 코드 수정을 하지 않습니다.
- 모든 기능 개발은 별도의 작업 브랜치에서 진행합니다.
- 기능별 브랜치를 생성하여 작업 내용을 독립적으로 관리합니다.
- 사용자의 명시적인 요청과 승인이 없는 Git 작업은 실행하지 않습니다.
- 기존 변경 사항을 임의로 삭제하거나 되돌리지 않습니다.
- 작업 전후 변경 사항을 확인합니다.

## 2. Git 상태 확인

Git 작업을 시작하기 전에 다음 항목을 확인합니다.

- 현재 브랜치
- Working Tree 상태
- Staged 및 Unstaged 변경 사항
- 기존 Commit 이력
- 원격 저장소 및 추적 브랜치
- 충돌 또는 진행 중인 Merge 여부

기존 변경 사항이 발견되면 사용자 작업인지 먼저 확인합니다.

기존 작업 내용이 남아 있거나 Working Tree가 깨끗하지 않은 경우 임의로 브랜치를 전환하거나 변경 사항을 처리하지 않습니다.

## 3. Branch 운영 규칙

### 3-1. Main 브랜치 보호

- `main`은 안정적인 프로젝트 상태를 유지하기 위한 브랜치입니다.
- `main`에서 직접 기능을 구현하거나 수정하지 않습니다.
- 새로운 기능 개발은 반드시 별도의 작업 브랜치에서 진행합니다.
- `main`에 직접 Commit하지 않습니다.
- `main`에 병합하는 작업은 사용자의 최종 승인 후 진행합니다.

### 3-2. 기능별 브랜치 생성

새로운 기능 개발 요청을 받으면 다음 순서로 진행합니다.

1. `Development_Status.md`를 확인합니다.
2. 기존 프로젝트 파일과 코드를 조사합니다.
3. 기존 기능의 구현 여부와 현재 상태를 확인합니다.
4. Git 상태와 현재 브랜치를 확인합니다.
5. 작업 브랜치 생성이 필요한지 판단하고 사용자에게 제안합니다.
6. 사용자의 승인을 받은 후 기능별 브랜치를 생성합니다.
7. 생성한 브랜치에서만 해당 기능을 개발합니다.

브랜치 이름은 다음 규칙을 사용합니다.

- `feature/player-movement`
- `feature/player-health`
- `feature/inventory`
- `fix/player-movement`

기능 개발은 `feature/기능명`, 버그 수정은 `fix/기능명` 형식을 사용합니다.

### 3-3. 브랜치 작업 범위

- 하나의 기능 브랜치에서는 하나의 명확한 기능을 개발합니다.
- 요청 범위와 관련 없는 기능을 추가하지 않습니다.
- 다른 기능의 코드 수정이 필요하면 사용자에게 먼저 설명합니다.
- 기존 작업 브랜치의 변경 사항을 임의로 덮어쓰지 않습니다.
- 작업 중 브랜치를 임의로 변경하지 않습니다.

## 4. Development_Status.md 연동

개발 진행 상황은 다음 문서에서 관리합니다.

`Docs/Workflow/Development_Status.md`

기능 개발 시 다음 내용을 기록합니다.

- 기능 이름
- 작업 브랜치 이름
- 현재 작업 상태
- 구현된 항목
- 미구현 항목
- 변경된 파일
- 코드 검토 결과
- Unity 테스트 결과
- 발생한 문제와 해결 여부
- 다음 작업

작업 상태는 다음 기준을 사용합니다.

- 미구현
- 진행 중
- 사용자 확인 대기
- 구현 완료

### 4-1. 작업 시작

기능 브랜치 생성 및 작업 승인이 완료되면 해당 기능의 작업 상태를 기록합니다.

### 4-2. 구현 진행

코드 수정 및 구현 상황이 변경되면 실제 프로젝트 상태에 맞춰 진행 상황을 갱신합니다.

### 4-3. 사용자 확인 대기

AI가 코드 구현을 마쳤더라도 사용자의 Unity Editor 확인이 끝나지 않았다면 `사용자 확인 대기`로 기록합니다.

AI가 임의로 `구현 완료`로 변경하지 않습니다.

### 4-4. 구현 완료

사용자가 Unity Editor에서 기능을 확인하고 명시적으로 구현 완료 처리를 요청한 경우에만 해당 항목을 `구현 완료`로 변경합니다.

## 5. Commit 규칙

- 사용자 요청 없이 Commit하지 않습니다.
- Commit 전에 변경 파일과 수정 내용을 설명합니다.
- 사용자의 승인을 받은 후 Commit합니다.
- Commit 메시지는 변경 목적이 명확하게 드러나도록 작성합니다.
- 관련 없는 파일을 하나의 Commit에 포함하지 않습니다.
- 기능별 작업 내용은 해당 기능 브랜치에 Commit합니다.
- `main` 브랜치에서는 기능 개발 Commit을 생성하지 않습니다.
- Commit 이후 실제 Commit ID를 확인하고 보고합니다.

## 6. Push 규칙

- 사용자 요청 없이 Push하지 않습니다.
- Push 대상 브랜치와 원격 저장소를 확인합니다.
- Push 전에 포함될 Commit과 변경 내용을 설명합니다.
- 사용자의 승인을 받은 후 Push합니다.
- 기능 브랜치를 Push할 때는 해당 기능 브랜치만 대상으로 합니다.
- `main` Push는 사용자가 Main 병합을 승인한 경우에만 진행합니다.
- Push 이후 원격 저장소 반영 여부를 확인하고 보고합니다.

## 7. Merge 규칙

### 7-1. Main 병합 조건

기능 브랜치는 다음 조건을 충족하기 전까지 `main`에 병합하지 않습니다.

1. 해당 기능의 구현이 완료되어야 합니다.
2. `Development_Status.md`에 진행 상황이 정확하게 기록되어야 합니다.
3. 사용자가 Unity Editor에서 기능을 확인해야 합니다.
4. 사용자가 해당 기능의 최종 완료를 승인해야 합니다.
5. AI가 변경 파일과 병합 대상 브랜치를 확인해야 합니다.

### 7-2. Merge 승인

- 사용자 요청 없이 Merge하지 않습니다.
- 기능 구현 완료 승인과 Main 병합 승인은 구분합니다.
- 사용자가 기능의 최종 완료를 승인했더라도 Merge를 자동으로 실행하지 않습니다.
- 병합 대상 브랜치와 변경 내용을 설명하고 별도의 승인을 받습니다.
- 승인 후 해당 기능 브랜치를 `main`에 병합합니다.

### 7-3. Merge 충돌

- Merge 충돌이 발생하면 임의로 해결하지 않습니다.
- 충돌 파일과 발생 원인을 설명합니다.
- 해결 방법을 제안하고 사용자 승인을 받습니다.
- 기존 작업 내용을 임의로 덮어쓰지 않습니다.

### 7-4. Merge 이후

- 병합 결과를 확인합니다.
- `main`의 현재 상태를 확인합니다.
- `Development_Status.md`에 병합 결과를 기록합니다.
- 기능 브랜치는 사용자 승인 없이 삭제하지 않습니다.

## 8. Branch 전환 및 삭제 규칙

- 사용자 요청 없이 Branch를 생성하거나 삭제하지 않습니다.
- 사용자 승인 없이 Branch를 전환하지 않습니다.
- 브랜치 전환 전 Working Tree와 변경 사항을 확인합니다.
- 작업 중인 변경 사항이 있으면 사용자에게 보고합니다.
- 기존 작업 브랜치의 변경 사항을 임의로 삭제하거나 덮어쓰지 않습니다.
- 병합이 완료된 브랜치도 사용자 승인 없이 삭제하지 않습니다.

## 9. 위험한 명령어

다음과 같은 명령은 사용자의 명시적인 승인 없이 실행하지 않습니다.

- `git reset --hard`
- `git clean -fd`
- `git push --force`
- 기존 Commit을 변경하거나 삭제하는 명령
- 작업 내용을 복구할 수 없게 만들 수 있는 명령

명령 실행이 필요한 경우 예상되는 결과와 위험성을 먼저 설명합니다.

## 10. 작업 완료 보고

Git 관련 작업을 수행한 경우 다음 내용을 보고합니다.

- 현재 Branch
- 변경된 파일
- Commit 여부 및 Commit ID
- Push 여부 및 대상 Branch
- Merge 여부 및 대상 Branch
- Merge 또는 충돌 발생 여부
- Development_Status.md 갱신 여부
- 추가 확인이 필요한 사항

실제로 실행하지 않은 Git 작업을 완료했다고 보고하지 않습니다.
