# Project Workflow Rules

이 문서는 AGENTS.md의 규칙을 따르며, 작업 유형별 진행 방식만 정의합니다.
세부 원칙(코드 작성, 테스트, Git, 진행 상황 관리)은 `AGENTS.md`를 기준으로 합니다.

## 1. 기본 지침

- 모든 답변은 한국어 존댓말을 사용합니다.
- 코드 식별자는 영어, 주석과 설명은 한국어로 작성합니다.
- 사용자가 가장 최근에 요청한 작업만 수행하며, 요청 범위를 벗어나지 않습니다.
- 이전 대화의 작업 목표를 현재 요청에 적용하지 않습니다.
- 확인하지 않은 파일, 변수명, 메서드명을 추측하여 작성하지 않습니다.
- 문서에 없는 설계나 규칙을 임의로 결정하지 않습니다.
- 요청의 대상이나 의도가 불분명하면 추측하지 않고 확인합니다.
- 내부 추론 과정과 `<think>` 태그를 답변이나 코드 파일에 출력하지 않습니다.

## 2. 작업 유형 판별

작업 시작 전에 사용자의 최신 요청을 아래 네 유형 중 하나로 판별합니다.
유형은 가장 최근 요청만으로 판단합니다.

### 2-1. 질문 및 개념 설명

- 질문의 핵심에 직접 답변합니다.
- 프로젝트 파일을 수정하지 않고, 작업 계획이나 Pending Actions를 만들지 않습니다.

### 2-2. 확정 수정

사용자가 수정 대상과 수정 내용을 구체적으로 지정한 경우입니다.
예: "PlayerMovement.cs의 GetAxis를 GetAxisRaw로 바꿔", "A를 B로 수정해"

- 지시 자체를 해당 범위에 대한 승인으로 간주합니다.
- 대상 파일만 읽고, 지시된 변경만 적용합니다. 지시 범위 밖은 수정하지 않습니다.
- 원인 분석, 대안 비교, 설계안, 확정 결정 대조표를 작성하지 않습니다.
- `AGENTS.md`, `Decisions.md`, `Development_Status.md` 등 상세 문서를 읽지 않습니다.
- 지시 내용이 `Decisions.md`의 확정 결정과 충돌할 가능성이 보이면 적용하지 않고 한 줄로 알립니다.
- 응답 첫 줄은 `[구현]`으로 표시합니다.
- 적용 후에는 변경한 파일, 변경한 줄, 이유만 짧게 보고합니다. 4장의 보고 양식은 사용하지 않습니다.
- 진행 상황 문서와 Git은 건드리지 않습니다.

### 2-3. 코드 제안 및 설계 제안

"코드를 보여줘", "적용하지 말고 보여줘", "설계안을 작성해줘"처럼 요청한 경우입니다.

- 기존 코드 확인과 분석은 허용합니다.
- 코드는 답변으로만 보여주고 프로젝트 파일은 수정하지 않습니다.
- 변경 이유를 설명한 뒤 사용자의 승인을 기다립니다.
- 새 시스템이나 구조 변경 설계라면 설계안 작성 전에 `Docs/Architecture/Decisions.md`를 확인합니다.
- 응답 첫 줄은 `[설계 제안]`으로 표시합니다.
- 설계안에는 확인한 파일 경로, 문제점과 원인, 변경 내용과 범위, 기존 시스템에 미치는 영향을 포함합니다.
- 범위 밖의 시스템 변경이 필요하면 "선행 작업 필요"로 보고하고 멈춥니다.
- 결정되지 않은 사항은 "미결정"으로 표시합니다.

### 2-4. 실제 프로젝트 구현

새 기능의 생성이나 구조 변경처럼 범위가 크고 구체적 지시가 없는 구현 요청입니다.

- `Docs/README.md`와 `Docs/Workflow/Development_Status.md`를 확인합니다.
- 작업과 관련된 상세 문서만 추가로 확인합니다. (5장 문서 목록 참고)
- 관련 파일과 기존 코드를 직접 조사하고, 이미 구현된 기능인지 확인합니다.
- 변경할 내용과 이유를 설명하고, "승인" 또는 "진행해" 같은 명확한 허락을 받은 뒤에만 파일을 수정합니다.
- 승인받은 범위만 수정합니다.
- 작업이 끝나면 4장의 보고 양식으로 보고합니다.
- 응답 첫 줄은 `[구현]` 또는 `[보고]`로 표시합니다.

## 3. Git 작업 금지

사용자가 현재 요청에서 Git 작업을 명시적으로 요청하지 않았다면 Git은 작업 범위에 포함되지 않습니다.

- `git status`, `git diff`, `git branch`, `git checkout`, `git switch`, commit, push, pull, merge를 실행하거나 계획하지 않습니다.
- Git 문서(`Git_Rules.md`)를 읽지 않습니다.
- Git 명령을 작업 계획, Pending Actions, 승인 대기 목록에 넣지 않습니다. "사전 확인"이나 "안전 절차"라는 이유도 허용하지 않습니다.
- 코드 구현 승인은 Git 승인이 아닙니다.
- Git 작업을 요청받으면 요청된 작업만 수행하고, 먼저 변경 내용을 설명한 뒤 승인을 받습니다.

## 4. 작업 결과 보고 양식

2-4(실제 프로젝트 구현)가 끝났을 때만 아래 양식을 사용합니다. 항목을 생략하지 않습니다.

- 변경한 파일:
- 변경 내용과 이유:
- 코드 실행 흐름:
- 기존 시스템과의 연결:
- 코드 검토:
- Unity 컴파일:
- 기능 테스트:
- 성능 테스트:
- 확인하지 못한 사항:

기록 규칙:

- 코드 검토는 실제로 수행한 경우에만 "완료"로 기록합니다.
- 실행하지 않은 Unity 컴파일과 기능 테스트는 "미실행", 측정하지 않은 성능은 "미측정"으로 기록합니다.
- AI는 Unity Editor, Console, Profiler를 볼 수 없으므로 확인한 것처럼 보고하지 않습니다.
- 확인하지 못한 내용이 없으면 "없음"으로 기록합니다.

이 양식은 `AGENTS.md` 7번과 동일하게 유지합니다. 한쪽을 수정하면 다른 쪽도 함께 수정합니다.

## 5. 문서 확인 (2-4 실제 프로젝트 구현에서만)

- 프로젝트 아키텍처: `Docs/Architecture/Overview.md`
- 설계 결정: `Docs/Architecture/Decisions.md`
- DOD 데이터 구조: `Docs/Rules/DOD_Rules.md`
- C# 코드 작성: `Docs/Rules/Coding_Standards.md`
- Unity 기능 및 MonoBehaviour: `Docs/Rules/Unity_Rules.md`
- 승인 및 작업 절차: `Docs/Workflow/Approval_Process.md`
- 테스트 및 성능 검증: `Docs/Workflow/Testing.md`
- 게임 기획: `Docs/GameDesign/Overview.md`
- Git 작업(요청받은 경우만): `Docs/Workflow/Git_Rules.md`

작업과 관련된 문서만 읽고, 이미 읽은 문서를 반복해서 읽지 않습니다.
문서가 없거나 비어 있으면 존재한다고 가정하지 않습니다.
문서 목록이 바뀌면 `AGENTS.md`의 8번과 함께 수정합니다.

## 6. 코드 작성 및 출력

- 기존 프로젝트의 코딩 스타일과 아키텍처를 우선하고, 기존 기능을 중복 구현하지 않습니다.
- `Rigidbody`와 `Rigidbody2D`처럼 다른 API를 혼동하지 않습니다.
- 주석과 `Debug.Log` 문자열에 이모지와 장식 기호를 쓰지 않습니다.
- 코드 파일에는 순수 C# 소스만 작성합니다. HTML 엔티티, Markdown 서식 문자, 불필요한 이스케이프(`\"`, `\<`, `\>`), 특수 토큰이 들어가지 않게 합니다.
- 파일 수정 후 실제 내용을 다시 읽어 위 오염이 없는지 확인합니다. 확인하지 못했다면 정상이라고 단정하지 않습니다.
- 코드 블록에는 파일에 복사할 코드만 넣고, 설명 문장은 블록 밖에 씁니다.
- 일부만 수정할 때는 변경 위치와 이유를 설명하고, 전체 코드를 요청받은 경우에만 전체 파일을 출력합니다.

## 7. 진행 상황 관리

2-4(실제 프로젝트 구현)에서 프로젝트 상태가 바뀐 경우에만, 작업 종료 시 한 번 `Docs/Workflow/Development_Status.md`를 갱신합니다.

- 상태: 미구현 / 진행 중 / 사용자 확인 대기 / 구현 완료
- AI가 코드를 반영하면 "사용자 확인 대기"로 기록합니다.
- "구현 완료"는 사용자가 Unity에서 확인하고 명시적으로 요청한 항목만 변경합니다.
- 질문, 설계 검토, 확정 수정에서는 문서를 갱신하지 않습니다.
- 갱신하지 못했다면 그 사실을 보고에 명시합니다.
