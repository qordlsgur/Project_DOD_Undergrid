# Project Workflow Rules

## 1. 기본 지침

- 모든 답변과 설명은 한국어 존댓말을 사용합니다.
- 코드 식별자는 영어, 주석과 설명은 한국어로 작성합니다.
- 작업을 시작하기 전에 `AGENTS.md`를 확인합니다.
- `Docs/README.md`와 `Docs/Workflow/Development_Status.md`를 확인합니다.
- 현재 작업과 관련된 상세 문서만 추가로 확인합니다.
- 문서에 없는 설계나 규칙을 임의로 결정하지 않습니다.
- 기존 프로젝트 구조와 코드를 먼저 확인합니다.
- 확인하지 않은 내용을 추측하여 작성하지 않습니다.
- 사용자가 요청한 작업 범위를 벗어나지 않습니다.
- 사용자가 이해할 수 있도록 설계 의도, 코드 실행 흐름 및 시스템 간 연결을 설명합니다.
- 내부 추론 과정(Chain of Thought)을 사용자에게 출력하지 않습니다.
- `<think>`, `</think>` 등의 내부 추론용 태그나 특수 토큰을 최종 답변에 출력하지 않습니다.

## 2. 작업 진행 순서

모든 개발 작업은 다음 순서로 진행합니다.

1. 사용자 요청과 작업 범위를 확인합니다.
2. `AGENTS.md`, `Docs/README.md`, `Development_Status.md`를 확인합니다.
3. 관련 문서와 기존 프로젝트 코드를 조사합니다.
4. 기존 기능의 구현 여부와 현재 상태를 확인합니다.
5. 변경할 내용과 이유, 예상 영향을 설명합니다.
6. 사용자 승인을 기다립니다.
7. 승인받은 범위 내에서만 코드를 생성하거나 수정합니다.
8. 실제 변경된 파일과 코드 실행 흐름을 확인합니다.
9. 작업 결과와 테스트 여부를 보고합니다.
10. 프로젝트 진행 상황에 변경이 있다면 `Development_Status.md`를 갱신합니다.

설계 제안 단계에서는 프로젝트 파일을 생성하거나 수정하지 않습니다.

## 3. 응답 단계 표시

모든 응답의 첫 줄에 현재 작업 단계를 표시합니다.

- `[설계 제안]`: 기존 코드 조사, 설계 및 변경 계획 설명
- `[구현]`: 사용자 승인 후 실제 코드 생성 및 수정
- `[보고]`: 작업 결과, 변경 사항 및 테스트 결과 보고

### 3-1. 설계안 작성 원칙

- 설계안을 작성하기 전에 `Docs/Architecture/Decisions.md`를 먼저 확인합니다.
- 이미 확정된 설계 결정과 충돌하는 설계를 제안하지 않습니다.
- 사용자가 요청한 기능의 범위 안에서만 설계합니다.
- 범위 밖의 시스템 변경이 필요하면 "선행 작업 필요"로 보고하고 멈춥니다.
- 사용자가 지적한 부분만 수정합니다.
- 아직 결정되지 않은 사항은 임의로 결정하지 않고 "미결정"으로 표시합니다.
- 설계안에 기존 Decisions와의 일치 여부를 명시합니다.
- 설계안에는 변경 대상 파일, 변경 목적, 주요 동작 방식 및 예상 영향을 포함합니다.
- 기존 기능과 중복되는 구현을 제안하지 않습니다.

## 4. 작업 유형별 문서 확인

작업 유형에 따라 다음 문서를 확인합니다.

- 프로젝트 아키텍처: `Docs/Architecture/Overview.md`
- 설계 결정: `Docs/Architecture/Decisions.md`
- DOD 데이터 구조: `Docs/Rules/DOD_Rules.md`
- C# 코드 작성: `Docs/Rules/Coding_Standards.md`
- Unity 기능 및 MonoBehaviour: `Docs/Rules/Unity_Rules.md`
- 승인 및 작업 절차: `Docs/Workflow/Approval_Process.md`
- 테스트 및 성능 검증: `Docs/Workflow/Testing.md`
- Git 작업: `Docs/Workflow/Git_Rules.md`
- 게임 기획: `Docs/GameDesign/Overview.md`
- 개발 진행 상황: `Docs/Workflow/Development_Status.md`

문서가 존재하지 않거나 내용이 없는 경우 임의로 존재한다고 가정하지 않습니다.

문서 목록이나 이름이 변경되면 `AGENTS.md`와 이 문서의 내용을 함께 수정합니다.

## 5. 사용자 승인 원칙

- 코드 및 시스템을 생성하거나 수정하기 전에 변경할 내용과 이유를 먼저 설명합니다.
- 신규 기능과 시스템은 설계안, 장단점 및 예상 영향을 먼저 제시합니다.
- 사용자의 명시적인 승인 전에는 프로젝트 파일을 생성하거나 수정하지 않습니다.
- 사용자가 "승인", "진행해" 등으로 명확하게 허락한 경우에만 승인으로 판단합니다.
- "좋아 보이네요" 등의 반응은 승인으로 간주하지 않습니다.
- 승인받은 범위를 벗어나 추가 기능을 구현하거나 리팩터링하지 않습니다.
- 기존 기능의 동작이나 아키텍처를 변경할 때는 별도 승인을 받습니다.
- 개선 사항이 발견되면 임의로 적용하지 않고 제안만 합니다.
- 경미한 오타, 주석 및 포맷 수정은 기존 동작에 영향을 주지 않는 경우 별도 승인 없이 처리할 수 있습니다.
- Git Commit, Push, Merge, Reset, Clean은 사용자가 명시적으로 요청하지 않는 한 실행하지 않습니다.

## 6. 코드 작성 및 출력 규칙

### 6-1. 코드 작성 원칙

- 기존 프로젝트의 코딩 스타일과 아키텍처를 우선합니다.
- 기존 시스템과 중복되는 기능을 새로 만들지 않습니다.
- 승인받은 범위 외의 로직, 구조, 변수명 및 실행 흐름을 임의로 변경하지 않습니다.
- 코드에는 실행 목적과 흐름을 이해할 수 있도록 자연스러운 한국어 주석을 작성합니다.
- 주석은 코드의 목적, 동작 이유 및 실행 흐름을 이해하는 데 필요한 내용만 작성합니다.
- DOD와 MonoBehaviour의 책임을 구분합니다.
- 불필요한 GC Alloc을 최소화합니다.
- 과도한 추상화와 불필요한 파일 생성을 피합니다.

### 6-2. 주석 및 로그 작성 규칙

- 주석에 이모지를 사용하지 않습니다.
- 주석에 장식용 기호나 감탄 표현을 사용하지 않습니다.
- `Debug.Log`, `Debug.LogWarning`, `Debug.LogError` 등의 로그 문자열에도 이모지를 사용하지 않습니다.
- 코드 생성 및 수정 후 주석과 로그 문자열을 확인합니다.

### 6-3. 코드 파일 인코딩 및 서식 오염 방지

- C# 파일에는 실제 C# 소스 코드만 작성합니다.
- HTML 엔티티(`&#x20;`, `&#x65;` 등)를 코드 파일에 기록하지 않습니다.
- Markdown 서식 문자(`**`, `*`, 백틱 등)가 코드에 잘못 포함되지 않도록 합니다.
- 문자열 내부의 따옴표를 제외하고 불필요한 역슬래시(`\`)를 추가하지 않습니다.
- `\"`, `\<`, `\>` 등 출력 과정에서 발생한 불필요한 이스케이프 문자가 실제 코드에 남지 않도록 합니다.
- C# 파일에 Markdown 코드 블록 표시 문자나 설명 문장을 포함하지 않습니다.
- `<think>`, `</think>` 등의 내부 추론용 태그나 특수 토큰을 실제 코드 파일에 포함하지 않습니다.
- 코드 생성 및 수정 후 실제 파일 내용을 다시 읽어 HTML 엔티티, Markdown 서식 문자, 불필요한 이스케이프 문자 및 특수 토큰이 포함되었는지 확인합니다.
- 문제가 발견되면 정상적인 C# 소스 코드로 복구한 후 결과를 보고합니다.
- 실제 파일 내용을 확인하지 못했다면 코드 파일이 정상적으로 작성되었다고 단정하지 않습니다.

### 6-4. 코드 출력 규칙

- 코드 블록에는 실제 파일에 복사할 수 있는 코드만 작성합니다.
- 코드 블록 안에 설명 문장이나 Markdown 장식을 넣지 않습니다.
- 기존 코드의 일부만 수정하는 경우 변경 위치와 변경 이유를 설명합니다.
- 전체 파일을 수정하는 경우 변경된 전체 코드를 제공합니다.

## 7. 테스트 및 작업 결과 보고

### 7-1. 테스트 관련 제한

- 실제로 실행하지 않은 테스트를 완료했다고 보고하지 않습니다.
- 측정하지 않은 성능 수치를 임의로 작성하지 않습니다.
- 코드 검토, Unity 컴파일, Test Runner 및 실제 플레이 테스트 결과를 구분합니다.
- AI는 Unity Editor를 실행하거나 Console, Profiler를 직접 확인할 수 없습니다.
- Unity 컴파일, 기능 테스트 및 성능 측정은 사용자가 수행하고 결과를 전달합니다.
- 사용자가 결과를 전달하기 전까지 테스트 상태는 "미실행" 또는 "미측정"으로 유지합니다.
- 테스트 중 오류가 발생하면 오류 내용과 해결 여부를 명확하게 보고합니다.

### 7-2. 작업 결과 보고

작업이 끝나면 다음 양식을 그대로 사용합니다.

- 변경한 파일:
- 변경 내용과 이유:
- 코드 실행 흐름:
- 기존 시스템과의 연결:
- 코드 검토: 완료
- Unity 컴파일: 미실행
- 기능 테스트: 미실행
- 성능 테스트: 미측정
- 확인하지 못한 사항:

항목을 임의로 생략하지 않습니다.

실제로 확인하지 못한 항목은 기본값을 유지합니다.

이 보고 양식은 `AGENTS.md` 7번과 동일하게 유지합니다. 한쪽을 수정하면 다른 쪽도 함께 수정합니다.

## 8. 개발 진행 상황 관리

`Docs/Workflow/Development_Status.md`는 프로젝트의 현재 진행 상황을 기록하는 기준 문서입니다.

### 8-1. 작업 시작 전 확인

- 새로운 작업을 시작할 때 `Development_Status.md`를 읽습니다.
- 사용자가 요청한 기능의 기존 진행 상태를 확인합니다.
- 관련 프로젝트 파일과 코드를 직접 조사합니다.
- 기존 기능이 이미 구현되어 있는지 확인합니다.
- 기존 구현이 있다면 구현된 내용과 확인 근거를 사용자에게 보고합니다.
- 구현되지 않았다면 미구현 상태와 필요한 작업을 설명합니다.
- 일부만 구현되어 있다면 구현된 부분과 남은 부분을 구분합니다.
- 기존 구현을 확인하지 않은 상태에서 중복으로 기능을 생성하지 않습니다.

### 8-2. 진행 상황 기록 항목

진행 상황 문서에는 다음 내용을 기록합니다.

- 완료된 작업
- 진행 중인 작업
- 사용자 확인 대기
- 미완료 작업
- 다음 작업
- 발생한 문제와 해결 여부
- 코드 검토 및 테스트 결과

### 8-3. 작업 상태 구분

다음 상태를 사용합니다.

| 상태 | 의미 |
|---|---|
| 미구현 | 해당 기능이 아직 구현되지 않은 상태 |
| 진행 중 | 일부 구현되었거나 현재 구현 작업 중인 상태 |
| 사용자 확인 대기 | AI가 코드 구현 및 파일 반영을 마쳤지만 사용자의 확인을 기다리는 상태 |
| 구현 완료 | 사용자가 확인하고 명시적으로 완료 처리를 요청한 상태 |

### 8-4. 구현 범위 판단 원칙

- AI는 실제 프로젝트 파일, 코드 및 시스템 연결 상태를 확인하여 구현 여부를 판단합니다.
- 사용자가 요청한 기능과 실제 구현된 기능의 범위를 구분합니다.
- 상위 시스템에 여러 하위 기능이 포함되어 있다면 각 기능을 개별적으로 확인합니다.
- 일부 기능만 구현된 경우 구현된 하위 기능만 기록합니다.
- 일부 기능을 구현했다고 상위 시스템 전체를 완료 처리하지 않습니다.
- 코드가 존재한다는 사실만으로 기능이 정상 작동한다고 판단하지 않습니다.
- 필요한 컴포넌트 연결과 실행 흐름도 확인합니다.
- 프로젝트 파일만으로 구현 여부를 확인할 수 없다면 "확인 필요"로 기록합니다.
- 실제 동작 여부는 사용자가 전달한 Unity 테스트 결과를 기준으로 판단합니다.

### 8-5. 완료 처리 권한

- AI는 작업을 수행했다는 이유만으로 작업을 완료 처리하지 않습니다.
- AI는 실제 구현 내용과 확인 결과를 기록하되, 최종 완료 여부는 사용자가 결정합니다.
- AI가 코드를 작성하고 실제 프로젝트 파일에 반영한 경우 해당 기능을 "사용자 확인 대기"로 기록합니다.
- AI는 Unity Editor에서 실제 동작을 확인할 수 없으므로 임의로 "구현 완료" 처리하지 않습니다.
- 사용자가 Unity Editor에서 확인한 결과를 전달하고 명시적으로 완료 처리를 요청한 경우에만 해당 기능을 "구현 완료"로 변경합니다.
- 사용자가 완료 처리를 요청하지 않았다면 "사용자 확인 대기" 상태를 유지합니다.
- 사용자가 추가 수정이나 보완을 요청하면 해당 기능을 "진행 중"으로 변경합니다.
- 사용자가 완료를 승인한 범위만 완료 처리합니다.
- 관련된 다른 기능까지 임의로 완료 처리하지 않습니다.

### 8-6. 진행 상황 기록 시점

- **작업 시작 전:** 기존 진행 상황을 확인합니다.
- **기존 구현 조사 후:** 기존 구현 여부와 확인 범위를 기록하고 사용자에게 보고합니다.
- **설계안 작성 후:** 설계 내용과 승인 대기 상태를 기록합니다.
- **사용자 승인 후:** 승인된 내용과 구현 예정 상태를 기록합니다.
- **코드 구현 후:** 실제 파일 반영을 확인하고 "사용자 확인 대기"로 기록합니다.
- **사용자 에디터 확인 후:** 사용자가 전달한 결과를 반영합니다.
- **사용자 완료 승인 후:** 승인된 항목만 "구현 완료"로 변경합니다.
- **작업 중단 시:** 중단 위치, 문제 및 남은 작업을 기록합니다.
- **작업 종료 시:** 진행 상황 문서와 실제 프로젝트 상태가 일치하는지 확인합니다.

### 8-7. 진행 상황 관리 주의 사항

- 기존 대화 내용을 추측하여 진행 상황을 작성하지 않습니다.
- 실제 프로젝트 파일과 현재 구현 상태를 확인한 뒤 기록합니다.
- 사용자의 승인을 기다리는 설계안이나 구현은 완료된 작업으로 기록하지 않습니다.
- 테스트하지 않은 기능을 테스트 완료로 기록하지 않습니다.
- 기존 진행 상황 기록을 임의로 삭제하지 않습니다.
- 단순 질문이나 코드 설명처럼 프로젝트 상태에 변화가 없는 작업은 기록하지 않습니다.
- 진행 상황에 변경이 없다면 불필요하게 문서를 수정하지 않습니다.
- 문서를 갱신하지 못했다면 그 사실을 작업 결과에 명시합니다.
- 문서 갱신 후 실제 프로젝트 상태와 일치하는지 확인합니다.
